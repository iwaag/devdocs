# zulip_receive — Step 3 report: context assembly and agent reaction

Date: 2026-08-12. Status: **complete**. A DM to the forge bot now produces an
immediate acknowledgement and then a real answer, generated by an agforge run
that was given the visible chat history rather than a single line.

## The wiring choice: route (a), called in-process

The plan offered two ways to connect the listener to an agent. Route (a) —
reuse the existing request pipeline — was chosen and confirmed by the
developer, with one refinement: the listener calls
`agent_run.run_request()` **directly in its own process** instead of POSTing
to its own `:8092`.

Why:

- **One charter.** `service/charter.md` holds roughly sixty lines of hard-won
  capability knowledge (generate.sh flags, the music service's self-describing
  guide, the ACE Studio hand-off). A chat-specific agent would have had to
  duplicate or diverge from it on day one.
- **The Agent ≠ Model record comes for free.** Every chat run writes the
  usual `.agent-run.json` with role, profile, harness, provider and model,
  because it *is* the usual run.
- **Fewer moving parts than the HTTP variant.** The literal route (a) would
  make the chat entrance depend on `serve.sh` being up and add a poll loop
  over HTTP for no gain; the pipeline is a function call away.

The cost, as the plan predicted: the pipeline's input field is named
`desire` and is now handed a conversation. That is absorbed in the desire
text itself (see below) rather than by renaming anything.

## What the agent receives

`src/agforge/zulip_chat.py` fetches up to 50 messages of the DM narrow,
oldest first, raw text (`apply_markdown=false`), and formats them one line
per message with the speaker's display name. The bot's own lines are labelled
`(you)`; its "on it" acks are stripped so they do not accumulate as noise.

```
[Developer] make me a small icon of a red bird
[Forge (you)] here's a small red bird icon: http://…
[Developer] same bird but blue
```

Around that transcript the desire explains the situation: this is a chat, the
last line is what to answer, earlier lines may carry the real subject, not
every message is a generation request, URLs are pasted verbatim, and the text
to send should go in a `reply` field of the usual `result.json`.

`reply` is a request, not a schema — the shell falls back through
`message`/`answer`/`text`/`detail` and finally posts the whole JSON in a code
block. Nothing is validated or rejected; the unshackle_agent rule that the
answer belongs to the agent still holds. Both this format and the `reply`
expectation are now documented in `service/GUIDE.md`, per "Tool Giving
includes usage info".

## Latency handling

The ack DM is sent before the run starts, carrying the request id. Each DM is
handled on its own thread, so the poll loop keeps running and a second
message does not wait behind a generation.

## Live evidence

Two consecutive DMs, both answered end to end:

| # | DM | Ack | Answer | Run |
|---|---|---|---|---|
| 1 | "make me a small icon of a red bird" | immediate | "here's a small red bird icon: <url>" | 31.2 s, sonnet |
| 2 | "same bird but blue" | immediate | "here's the blue version: <url>" | 31.3 s, sonnet |

- Both presigned URLs were fetched and returned HTTP 200 `image/jpeg`
  (65 KB and 44 KB). They arrive in the chat as plain links.
- The second run is the history check that Step 4 asks for, arriving early:
  "same bird but blue" carries no subject of its own, and the agent both
  answered as a continuation ("the blue version") and produced a bird. The
  image itself contains two birds rather than one recoloured one — generation
  quality is a non-goal here, and the context plainly reached the agent.
- The listener log records the backend per run, as the constraint requires:
  `role=generator profile=sonnet harness=claude_code
  provider=anthropic model=anthropic/claude-sonnet-5`, with cost and duration.
