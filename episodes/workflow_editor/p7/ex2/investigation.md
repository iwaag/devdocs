# 右ペインの入力・スクロールに関する調査と修正方針

## 結論

修正が必要。run画面の右ペインを更新するたびに子DOMを全破棄しており、入力文字列を復元してもIMEの変換状態や内部スクロールは維持できない。更新頻度を落とすだけでは解決しない。

今回は調査と方針提案まで。製品コードは変更していない。

## 調査対象と確認範囲

- 2026-10-12、`pj-agdev/agdevworld` の `6058c0f`。
- 現行ソースの `workflow_editor/src/runView.ts` を中心に、監視、実行状態API、既存ブラウザー検証を確認。
- 本番のレジストリやrunは操作せず、使い捨てプロジェクト・サービス・Chromiumで再現確認した。
- 稼働中サービスの配布リリースとの一致は未確認。「ログとチャット」は現行run画面のHistory／ファイル表示とQuestionsを中心に調査した。別画面固有の問題まで確認したという意味ではない。

## 原因

### 1. 右ペイン全体を再構築する

`runView.ts:364` の `renderSide()` は、フォーカスと選択範囲を取得した後、369行目の `side.replaceChildren()` で子要素をすべて破棄する。質問への回答欄、各種フォーム、ファイル表示、履歴が毎回新規作成される。

`drafts` に入力文字列を保存し、430行目以降で `focus()` と `setSelectionRange()` を実行しているので、通常の文字入力は残る。しかしこれは元の入力要素を維持する処理ではない。IMEの変換状態、textarea内部やファイル表示のスクロール、テキスト選択などは復元されない。`focus()` に `preventScroll` がない点も表示位置を動かす要因となりうる。

さらに、選択ノード内の質問とQuestions一覧には同じ質問が重複表示され、同一の `data-focus-key="answer:<id>"` が付く。復元先を `querySelector` で選ぶため、別の回答欄にフォーカスが移る可能性がある。

### 2. 実行状態の生存確認だけでも再構築される

`runView.ts:652–660` は3秒ごとに実行・通知・プレゼン状態を取得し、レスポンス全体の `JSON.stringify` 比較で変化があれば右ペインを再構築する。

実行状態には `executor.at` が含まれる（`server/exec.ts:450–466`）。autolabは約2秒＋処理時間ごとにheartbeatを書き込む（`agautolab/src/agautolab/wfexec.py:72,218–220,313`）。このためrunの進捗が変わらなくても、executor稼働中は生存確認時刻の変化が右ペイン再構築の引き金になる。現状のExecution表示ではこの時刻そのものは表示していない。

### 3. SSE更新でも全体が再構築される

`runView.ts:637–646` のイベント受信で `load()` → `render()` → `renderSide()` が呼ばれる。接続状態の変化でも `render()` を呼ぶ。`server/watch.ts:106–153` はrun.jsonだけでなくrunフォルダ内のファイル変更もrunイベントにするため、レポートなどの更新も影響する。

30秒の時計更新は `renderSummary()` のみなので、右ペイン破棄の直接原因ではない。SSEのkeep-aliveコメント自体も再描画の原因ではない。

## ブラウザーでの確認結果

現行ソースの `npm run build` は成功。既存 `checks/runs.ts` の隔離fixtureを利用した一時的な検証で、質問待ちrunの表示中に `node.progress` を記録し、SSE更新を発生させた。

| 確認項目 | 更新前 | 更新後 |
| --- | --- | --- |
| CDP `Input.imeSetComposition` で入力した文字列 | にほんご | にほんご |
| 変換を開始した元のtextarea | DOMに接続 | DOMから切断 |
| フォーカス先 | 元のtextarea | 新規作成された別textarea |
| ファイル表示 `pre.scrollTop` | 400 | 0 |
| ファイル表示 `pre.scrollLeft` | 80 | 0 |
| 右ペイン外枠 `scrollTop`（フォーカスなし） | 600 | 600 |

ページのJavaScriptエラーはなし。入力要素の破棄と内部スクロール消失は実測で確認できた。macOSの日本語IME候補ウィンドウの具体的な動きは手動未確認であり、CDP検証と区別する。

既存の `checks/runs.ts:149–159` は回答文字列とフォーカスの保持だけを確認しており、この不具合を検出できない。

## 推奨する修正方針

### 主修正：入力欄と閲覧領域のDOMを維持する

右ペインを一度組み立て、更新対象のセクションと表示値だけを更新する構造にする。新しいUIフレームワークの導入は不要。

- 質問カードは質問IDで管理し、本文・状態・回答一覧を更新する。回答フォームは同じ質問が継続する限り同じDOMを使う。ノード詳細と一覧で重複表示する場合は、表示場所と質問IDの組み合わせで要素を識別する。
- 入力中の `value` をバックグラウンド更新で書き戻さない。名前・回答・再開指示・定義調整・判定根拠など、右ペイン内の全入力欄を対象にする。
- ファイル表示のスクロール要素を維持する。同じファイルの更新では位置を保ち、別ファイルを開いたときだけ初期位置にする。
- 履歴はseqをキーに既存行を保持して追加・更新する。上部に行が増える場合は、読んでいた項目を基準に表示位置を補正する。単純なscrollTopの復元だけでは上への挿入に対応しない。
- 外部更新で質問が取り下げられた場合など、フォームの有効性が変わるケースも扱う。変換中は対象入力を破棄せず、送信時には最新の質問状態・run状態を確認し、既存のexpectSeqによる競合検出を維持する。

`compositionstart/end` 中だけ再描画を延期する方法は暫定策にはなるが、スクロール問題や変換外の入力中断を解決しないため主修正にはしない。

### 併せて行う修正：更新範囲と更新管理を限定する

- heartbeat時刻だけの変化は、実行状態の判定に反映しても入力・履歴セクションの再描画には使わない。available/unavailableなど必要な表示変化は引き続き反映する。
- 接続状態が変わったときは接続表示・必要なバナーを更新し、再接続時のデータ再取得は維持する。
- ポーリングとSSE再取得の結果適用を整理する。非同期ポーリングの重複、古いレスポンスによる巻き戻し、画面破棄後の適用を防ぐ。現状の `load()` 用serialだけではポーリングとの並行実行は制御されない。
- フォーカスを明示的に移す必要がある操作では `preventScroll: true` を検討する。通常のバックグラウンド更新ではフォーカスを取り直さない。

更新を止める／ポーリング間隔だけを延ばす／スクロール値だけを保存復元する、という対応では根本原因が残る。

## 修正後の受け入れ条件

1. 変換中にheartbeat、run進捗、ファイル変更、接続断・復旧が来ても、対象textareaのDOM同一性と変換が維持される。macOS日本語IMEでも手動確認する。
2. 回答・名前・再開指示・定義調整・判定根拠の下書き、選択範囲、入力欄内部スクロールが保たれる。重複表示された質問間でフォーカスが移らない。
3. ファイルの縦横スクロールと履歴の読んでいる位置が保たれる。履歴の追加や他セクションの高さ変化も含める。
4. 入力中でも実行状態・進捗の更新は継続し、無効になった操作や競合する送信は適切に拒否される。
5. 遅い通信、ポーリング中のrun切り替え・画面離脱で、古い応答が新しい表示を上書きしない。

既存ブラウザー検証にこれらの回帰確認を加え、型検査・既存run検証・production buildを実行する。
