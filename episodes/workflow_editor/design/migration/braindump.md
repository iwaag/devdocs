# 本システム組み込み展望

p3でrunの実行をエージェントと共同で完遂した。
そろそろ本システムへの移行を検討したい。
が、その前に十分に計画を検討したい。
本システムは複数のエージェントの協調を前提にしており複雑で、かつ開発途上なので、段階を経ずに一気に合流すると本質的なではない問題に時間を費やす可能性がある。

最初は一体のエージェントで完結させる。autolabだけで完結させる。frontもforgeも連携しないし、studyもarchsageを用いない。
その上で、何をdevdocsに残し、何をzulipに残すかを考える。
zulipは主に協調のためのツールなので、autolab単体で完結する場合には必要性は下がるが、今後frontに監視させるなどの連携を実装するフェーズになったら意味を持ち始めるだろう。
その上で、目標として今回実験環境で作ったeditorをagdevworldに組み込んだ上で、その管理下プロジェクトであるRTS開発プロジェクトをagdevworld上から開発継続できるようにする。

# 要件

要件として、現在ローカルフォルダで擬似的にやってるリモートリポジトリはgiteaに移行する。

devdocsは少し仕様を変える。プロジェクト作成時、ルートの１フォルダとして進めるパターンと、今のように別リポジトリとして進めるパターンを選べるようにする。１フォルダとして運用するパターンをデフォルトとする。途中で変えたくなったときのことは今は考えなくていい。

また、UI画面にも要件を加える。
全プロジェクト一覧と、studyやwedoなどの共有サブリポジトリ一覧を俯瞰的にみられる画面が欲しい。
このシステムで管理しているほぼ全てのリソースに該当しそうだから、agdev dashboardとでもいうべきだろうか？
プロジェクトエディタはあくまでプロジェクトのリソース一覧なので、混同してはいけない。ただ、プロジェクト途中でプロジェクトに既存のサブリポジトリを追加インポートする可能性とかはあるので、関連はある。

また、長期的な展望として、agfrontやagforge、agautolabはじめすべてのagagエージェントをプロジェクトの一形態としてとらえ、プロジェクトに(主にzulip経由の)エージェント実行のための情報を加えたものをエージェントの実体としたい。これは移植が進んでプロジェクトやワークフローの仕様も十分に固まってから手をつける。

# devdocsの運用について

<workflow-id>/runs/<run-id>/の順番を入れ替え、runs/<workflow-id>/<run-id>/に変更する。ルートに大量の固有名フォルダが並ぶのは望ましく無いと感じるから。

また、作業記録の正本はdevdocsとする。永続性や文字量という点で明らかにそちらのほうが扱いやすい。zulipはエージェント同士やエージェントと人間の連携のための機構という位置付けを踏まえて、zulipの方には連携をたすける概要のみを書き込み、細かい記録はdevdocsに任せる。これはzulipの内容を単純に減らすというより、連携のための記録に特化するという意味だ。おそらくテキスト量は減るが、連携の方針によっては頻度はひょっとしたら上がるかもしれない。

# delegateについて

delegateはまだテストしていないが、これは同一プロジェクト無いのワークフローに限らず、異なるプロジェクト/エージェントのワークフローに関わる可能性があるから、複数エージェント前提になったときに改めて考える。今はいったん形だけで実体は無くていい。

# 後方互換について
