# Workflow editor p8/ex2 — 活動表示・作成導線・基本ワークフロー

## 目的と合意事項

[braindump.md](braindump.md)と、その後の相談で合意した方針を実装する。

1. Simpleの少ない情報量を維持し、runが動いていることを細かいログなしで実感できるようにする。
2. Simpleから新しいワークフローを作成できるようにする。
3. 全プロジェクトに基本ワークフロー`freework`を用意する。braindumpとtalkノード一つから始め、会話を通じて実行計画を追加・変更して進める。
4. freework専用の実行機構を作らない。ポリシー、会話、作業追加、終了判定、活動表示はすべて通常のワークフローに共通適用する。
5. 初回の計画相談は強制追加ではなく、選択したポリシーの結果として生成する。

実装対象は主に`pj-agdev/agdevworld/workflow_editor`。実行側の連携が必要な場合は、その呼び出し元と共通ガイドも対象にする。今回は計画の作成までであり、実装・運用データへの追加・デプロイはまだ行わない。

## 現状と設計上の注意

- `src/runView.ts`のSimpleのバーは作業ノードの完了数を表示する。ノード内の活動は反映されず、実行プロセスの情報もDetail側にある。
- `src/projectView.ts`の新規ワークフロー作成フォームはDetail専用になっている。
- 現在のドキュメントポリシーは`default`と`manual`。前者は計画相談・各ノード報告・最終報告をまとめて生成し、後者は生成しない。
- `shared/compile.ts`だけでなく、実行ガイド、検証、runの読み込み、調整、描画にもポリシー名による分岐がある。設定の追加だけで完了とはしない。
- run adjustmentは未着手の作業を変更する既存機構。実行中ノードがない境界で適用し、開始済みの意味・履歴は保存する。完了済みrunには適用できない。
- 定義のリポジトリ権限や実行設定は途中のadjustmentでは変更できない。freeworkにも開始時からプロジェクトに適した明示的な設定が必要。

## 1. 共通のドキュメントポリシー

### 利用者に見える設定

自動追加する以下の三項目を独立して選択可能にする。

| 項目 | 従来の標準設定 | freeworkの初期設定 |
| --- | --- | --- |
| 計画の相談 | あり | なし |
| 各ノードの報告 | あり | なし |
| 最終報告 | あり | あり |

freework自身のtalkが初回相談を担う。最終報告を残すことで成果と終了を示し、作業追加前に最初のtalkだけでrunが完了することも避ける。ただし最終報告開始前の作業追加を保証する共通手順は別途必要。

### データと互換性

- 既存の`default`と`manual`の意味は変更しない。個別設定用の表現を追加し、正規化した三項目をコンパイラ・検証・実行ガイドで共有する。保存形式は実装の最初に確定し、契約文書に例を記す。
- 不正値や矛盾した指定は明示的に拒否し、読み込み時に黙って補正しない。
- 新しいコンパイラの版を記録し、選ばれた項目に応じてエッジを正しく接続する。生成されないreportを前提にした最終報告の指示も修正する。
- 作成済みrunの固定グラフ、生成ステップの指示、履歴は再生成しない。既存runの読み込みと履歴再生を維持する。
- run中のポリシー変更は従来どおり禁止する。ポリシー名だけでなく正規化した設定全体を比較する。
- UI・進捗集計・ガイドは`policy === 'default'`という判定から、実際の生成ステップと有効設定を参照する形へ整理する。
- 計画相談を無効にしても、質問への回答、変更範囲の合意、結果の承認を混同しない。実行完了が結果の承認を意味しない既存の原則を保つ。

## 2. 会話から作業を追加する共通実行手順

どのワークフローでも、次の手順で実行計画を育てられるようにする。

1. braindump、回答、追加指示を確認し、必要な作業と変更理由を整理する。
2. 開始済みノードを維持した変更案を作成し、既存のdry-runで検証する。
3. ノード境界でadjustmentを適用する。
4. 更新後のグラフから次のノードを選ぶ。追加の必要がなければ既存の終端へ進む。

元の依頼の範囲内なら既存の`request`、回答や指示に基づく変更なら対応するsourceを利用する。範囲変更の合意には既存の`agreement`を使う。グラフを具体化するたびに新しい確認操作を増やさない。

### 最初に実証する境界条件

- talkの回答を取り込み、talkを完了してから、最終報告が始まる前に作業を追加できること。
- 追加後の作業を実行し、必要なら新しいtalkと後続作業を追加できること。終了したtalkを再利用・書き換えないこと。
- 各ノード報告がある設定でも同じ手順が成立すること。
- 最終報告がない設定で終端ノードの完了時に追加予定がある場合、先に完了扱いになる問題がないこと。

最後のケースが既存APIでは成立しなければ、一般の「ノード完了と後続変更の確定」を同一ロック下で扱う操作など、必要最小限の共通拡張を設計する。完了後のrunを暗黙に復活させたり、freeworkだけ完了を保留したりしない。追加作業のない通常のワークフローは従来どおり完了する。

変更の失敗、古いseq/revision、二重適用、実行プロセスの再開でも、作業が消えたり重複したりしないことを確認する。開始済みステップの保護、権限の固定、attemptの所有権、未処理指示の扱いは維持する。

## 3. freeworkを基本ワークフローとして配置

- 通常のワークフロー定義として配布する。IDは`freework`、初期の著者定義ノードはtalk一つ。braindumpは既存のrun入力を使う。
- talkの説明は「依頼を理解し、必要な相談を行い、次の作業を具体化する」とする。グラフを更新する具体的な手順は共通実行ガイドへ置く。
- 基本ワークフローの配置は、新規プロジェクトの作成と既存プロジェクトへの補完で同じ仕組みを使う。
- プロジェクトごとの正規の定義配置先、リポジトリbindings、実行設定を解決して生成する。全リポジトリへの編集権限や外部連携の有効化を一律に付与しない。
- 既存プロジェクトへの追加は冪等にする。同じファイルまたはIDがある場合は上書きせず、競合・不正な既存定義は理由付きで報告する。
- 複数workspaceや共用devdocsがある場合は重複追加を避ける。対象を事前列挙するdry-runと、追加・既存・競合・追加不能の結果一覧を用意する。
- 通常の画面表示や読み取りAPIでファイルを作成しない。新規作成処理と明示的な補完処理で追加する。
- 利用者による編集を保存し、以後の更新で標準内容を強制しない。
- freeworkという名前によるランタイム分岐を作らない。名前を変えた同一構造のワークフローでも動作することを検証する。

会話で育った定義は当該runのrevisionに保存する。再利用する定義への書き戻しは自動で行わない。「ワークフローとして保存」は将来の拡張とし、今回の必須範囲から外す。

## 4. Simpleの新規作成と開始導線

- プロジェクトのワークフロー一覧に「＋ ワークフローを作成」を常設し、一覧が空でも同じ入口を示す。
- Simpleのまま最小限の入力で作成できる。技術的なIDと詳細ポリシーは必要に応じて開く設定へ置き、入力エラーはその場で修正可能にする。
- 通常の空の定義と基本テンプレートから作成できる形にする。テンプレート選択は汎用の入口として実装する。
- 配置済みfreeworkは通常の一覧・run依頼フォームから選び、braindumpを書いて開始する。開始のたびに定義を複製しない。
- Simple/Detailの切り替えや背景更新で入力、選択、スクロールを失わない。
- 共通ポリシーの編集と生成グラフのプレビューを整合させる。Simpleの初期画面には詳細設定を並べない。

## 5. 実データに基づく活動表示

### 表示契約

既存の完了ステップ数に加え、現在の作業名・活動数・最終活動からの経過を短く表示する。

例：`実装中 · 更新24回 · 最終更新8秒前`、`3ステップ完了 · 現在は検証中`。

- バックエンドに安定したターンイベントがあれば「ターン」、更新イベントしかなければ「更新」と、実際に数えた対象を示す。定義できない数は出さない。
- 実装開始時にログ形式・イベント・既存APIを調査し、活動数の単位と集計範囲を決める。生ログや機密をSimpleへ転送せず、小さな共通サマリーを提供する。
- 接続のheartbeatやポーリング成功をエージェント活動として数えない。プロセス生存、最後に観測した活動、作業完了は別の事実として扱う。
- 再接続や再取得で二重計上しない。再試行をまたぐ累積値か試行単位かを明記し、リロードで値が矛盾しないようにする。
- 回答待ち・キュー待ち・停止・失敗・完了・切断はそれぞれ適切な状態を示す。切断時に観測できない活動を断定しない。履歴表示に現在の活動を混ぜない。
- 実際の更新時に控えめな視覚フィードバックをつける。動きを減らす設定を尊重し、秒単位の読み上げ通知で操作を妨げない。
- 作業追加で総数が増えることを考慮し、動的なグラフでは完了数と現在の作業を中心にする。完了率を時間の見積もりとして扱わない。

## 実装順序と成果物

| 段階 | 作業 | 完了条件 |
| --- | --- | --- |
| 0 | checkout・配備版・既存テスト・実行連携・活動データを調査 | 変更対象、ポリシー保存形式、活動の集計単位、境界処理の不足を記録 |
| 1 | Simpleの新規作成入口を改善 | Detailへの切り替えなしで作成できる |
| 2 | 共通の活動サマリーと表示を実装 | 長いノード内でも実際の活動更新が見え、待機や切断と区別できる |
| 3 | 個別ポリシーと互換性を実装 | 三項目の全8組み合わせでコンパイル・検証・描画・実行ガイドが一致 |
| 4 | 会話→作業追加→実行→追加相談→終了を実証し共通手順を整備 | 最終報告あり／なしを含め境界で追加でき、途中再開しても整合性を維持 |
| 5 | freework定義・新規配置・既存補完・開始導線を実装 | 新規プロジェクトに存在し、既存補完は冪等で利用者の定義を保護 |
| 6 | 統合検証・画面確認・契約文書と実行ガイド更新 | 下記の受け入れ基準を満たし、結果と残る制約をreportに記録 |
| 7 | リリースと既存プロジェクトへの補完 | 対象と変更を記録し、配備版・補完結果・復旧手順を報告 |

段階7では、新形式を扱える実行環境の配備を先に行い、その後で基本ワークフローを補完する。旧版に戻す場合の新形式定義・runの扱いも確認し、旧版が読めるとは仮定しない。計画作成時点では段階7を実行しない。

## 検証と受け入れ基準

実装・ブラウザー検証は隔離したサービスとfixtureで行う。運用データは初期調査では読み取りのみとする。

- **Simple**：長い作業中の活動が分かり、細かいログ・ID・パスを常時表示しない。作成、入力保持、質問への回答がSimpleだけで完結する。
- **ポリシー**：全組み合わせのグラフ接続、生成ステップ数、成果物の要件をテストする。旧形式の読み込み、保存、固定グラフの履歴再生を回帰確認する。
- **変更**：作業追加を二巡するケース、範囲変更、質問待ち、再起動、競合、失敗からの再試行を確認する。開始済みノード・アクセス・ポリシー変更の拒否も維持する。
- **一般性**：freeworkと異なるID、既存の複数ノード構成、最終報告のない構成でも共通の変更手順を確認する。
- **配置**：新規、既存未配置、配置済み、利用者編集済み、同名衝突、追加不能、重複workspaceを検証する。補完を再実行しても変更が増えない。
- **活動**：重複イベント、再接続、ログ取得不能、再試行、別ホスト、履歴閲覧でも誤った活動を表示しない。
- **統合**：`npm run check`と関連する既存の表示・会話・実行・調整・生成ステップのチェックを実行する。1440×1000と1280×800で主要状態を確認し、Simpleの情報量が逆戻りしていないことを確かめる。

変更点、検証結果、実装済み／配備済みの区別、既存プロジェクトへの補完結果をこのディレクトリのreportに残す。
