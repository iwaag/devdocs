cagentが管理しているPCクラスターの情報をcontextに反映する仕組みがほしい。

クラスターの情報は基本的にバージョン管理に含める情報ではない。実験条件として一般化したスペック情報として実験報告などに含めることはあるだろうが、pc-AがどんなGPUでRAM何Gbで稼働しているかとか、いま現在comfyuiがどのPCでどんなURLで起動しているか、とかはバージョン管理するような情報ではない、というか、場合によっては秘匿情報の漏洩だ。

だから、一般情報はoverride system contextが多分一番適しているはず。プロジェクトからcontextをいじる方法が必要だ。
ただ、一つ気がかりなのは、誰でも書き換えできる形でただcontextに書けばいいという単純な話かどうかということだ。いまは実験フェーズなので厳密に読み書き可能な境界を保護する必要はないが、少なくともインターフェイス層でcagentが書いた部分がcagent管理のひとかたまりの情報として視覚的に明確にわかるよう、GUIの表示がわかりやすくなっていてほしい。そうすれば、cagentが書いた情報、人間が加えた情報、他のエージェントの書き込みが区別しやすい。

その上で、comfyuiがすでに立ち上がってるとか、agstudioはメモリがいっぱいあってollamaも立ち上がってるとか、agpcにcuda使えるGPUがあるとかクラスター情報がプロジェクトに共有されれば、立ち上がったばかりのプロジェクトがどこに計算サービスを立ち上げようか、などという判断も即座にできるようになるはずだ。

ただし、クラスター情報を全て一つのコンテキストにまとめると量が膨大になる。contextに与えるのは、ごく短く簡潔な概要と、さらに詳しい情報を知りたいときのcagentへの質問先もしくは詳細情報の辿り方をしめすような形にしたほうがいい気がする。system wideで強制的に付与されるからこそ、その分量はごくごく短く絞る必要がある。たとえば「このクラスタには大メモリのagstudioとcuda readyのagpcがある。よく使われるサービスはcomfyuiでurlは…」みたいな感じでいいかもしれない。

一番いいのはcagentが他のプロジェクトの概要を把握した上でoverride project contextとしてプロジェクトに特化したコンテキストを何らかのタイミングやトリガーで作ってあげることかもしれない。たとえばoverride forge project contextとして、アセット生成に有用な情報は重点的にして「comfyuiはモデルが6個インストールされていて最後の導通確認は何月何日に行われた。」とか与えられるのがいいかも。それが洗練されていけば、確認のためのコミュニケーションが減らせる。
