## What the phase did

p8 moved an agent's memory of "whose behalf am I here on" out of a ledger
file and into the conversation. autolab was the one agent left out of it: it
still imported `agag.participation`, was pinned to the pre-p8 pyagag, and
read a `workrun-` topic's binding out of the topic's *name* and its channel's
*description*.

It is in now, and three things travel with it:

1. **A `workrun-` topic says what it is for.** Planning opens it with a
   `[selfnote][rootchat]` note naming the mission conversation — whose
   `pj-<slug>` channel is the project — and a `[selfnote][work]` note naming
   its Plane Sub-Work, before the visible description. The name and the
   channel description decide nothing; the description is still written, for
   whoever opens the channel.
2. **A callback answers at home.** A mention in a topic carrying autolab's
   root note serves that task, places the remote beside the chatlog as a
   thread, and replies **in the task's own topic**. Speaking to the other
   agent is a deliberate `agentchat send`.
3. **A served callback is marked**, `[selfnote][served] <channel>/<topic>
   <id>` into home, so recovery does not run a supercoder twice over a live
   repository.

Two of p8's open items were prerequisites rather than deferrals, and both are
closed: forge names the trigger **once** (in the delivery, not the run
report), and the startup sweep has a served marker.

## What the phase actually cost, and bought

Three attempts failed before the clean one. **The mechanism this phase built
was never what failed** — anchoring, callback lookup, replies at home, served
markers and restart safety behaved identically on all four runs. What failed
was the machinery around it, and the mission is what found it. Five
pre-existing defects, each with a regression test:

| where | what it was | fix |
|---|---|---|
| agforge | an assetplan *question* named nobody, because the naming post is the final reply and a question has no final body | `7e1749b` |
| agautolab | the planning reply said `opened <topic>` and never that a post is what starts it; the supervisor waited for work nobody had triggered | `69be43e` |
| agforge | "the trigger" was read by re-reading the run topic, so a supervisor's mid-generation check-in collected the delivery | `dabea97` |
| pyagag | the callback lookup did not follow Zulip's `✔ ` rename, so every task's completion report was dropped — the post that names the supervisor is the post that ends the conversation | `938d3ab` |
| pyagag | `sweep_mentions` had no notion of "already answered"; it used to silence itself, and stopped doing so when p8 sent the answer home | `65bd3b2` |

Four of the five are the same shape: **being named is how the next run
happens at all**, so anything that loses a name, misdirects one, or replays
one is a workflow that stops or repeats. p8 made that the whole turn-taking
rule; p9 is where its edges got walked.

The fourth is worth naming on its own, because it is the phase's sharpest
lesson. The mission stopped for 26 minutes with three agents idle and **not
one line in any log saying anything was wrong** — every component reported
success, and the conversation simply had a hole in it. Recovering it took no
human post at all: the listeners were fixed and restarted, and Front's
startup sweep found the five callbacks it had been dropping and carried on
from task 3. The memory is in the chat, so a listener that learns to read it
again remembers where it was.

## Open

### Carried from p8, still open

- **Silent mentions.** p7 listed `@_**name**` as a terminator candidate; p9
  did not need it either. `handoff=False` turned out to be the answer to the
  question it was proposed for.
- **Two root-noted agents named by one post.** Still untested live.
- **Selfnote accumulation.** Now real rather than theoretical: a home
  collects a `[served]` note per callback. `LAST_SPEAKER_LOOKBACK` went 10 →
  30 for it. Nothing prunes them.
- **Video.** Untouched.

### Found in this phase

- **The mission Work is never closed.** Every Sub-Work of S2-30 is
  `completed`; S2-30 itself is `unstarted`. Front triggered the tasks
  directly rather than through `start.flag`, and nothing transitions a
  mission when its last task finishes.
- **A cancelled plan Work is revived silently.** forge keys a plan by
  `<channel>/<topic>`, so a new `assetplan-` topic of the same name upserts
  onto the old Work — attempt 4's sprite ran as F2-17, which p6's cleanup had
  Cancelled.
- **Residue should be deleted, not resolved.** Resolving p6's forge topics
  made their names poisonous: a registered plan whose run topic is resolved
  can never be run again, because `open_assetrun` is idempotent by its work
  note. Two attempts were spent on that before the topics were deleted.
- **`unknown toolset 'toolset'; skipped`** in every forge assetplan run — the
  front's `toolsets.csv` header row is read as a name.
- **One stray topic**, `work-s2-30/workrun-task1-s2-30`, holding a selfnote
  and an empty reply. The write-side rename bug, fixed after it made this;
  left as evidence.

### The question p9 leaves for p10

Every defect in the table above was invisible until an agent ran into it, and
four of the five were silent — no exception, no error line, a listener that
looked healthy and a conversation that had simply stopped. The workflow has
no way to notice that it is stuck. A supervisor waiting for a callback that
will never come looks exactly like a supervisor waiting for a slow one, and
in this phase only a human reading the chat could tell the difference.
